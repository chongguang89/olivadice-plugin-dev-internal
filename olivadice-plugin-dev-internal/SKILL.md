# 青果骰插件开发

编写、修改、审查并打包**青果骰**的 QQ 机器人插件。

名词对应关系（别搞混）：

- **青果骰**，英文名 **OlivaDice** —— 就是骰主在用的那个骰子；
- **OlivOS** —— 承载青果骰的框架，插件运行在它之上；
- **OlivaDiceCore** —— 青果骰的核心插件本体，插件接口大多由它提供。

目标平台是 QQ（napcat / LLBot 等 OneBot 实现），运行环境是骰主自己的服务器。

**本 skill 不负责安装插件**。骰子在骰主的服务器上，交付物是插件源码文件夹或一个 `.opk`，由骰主自行安装。

## 铁律

### 必须先做

1. **先澄清再动笔。** 写任何一行代码前，必须走完第 0 步的需求澄清。任何有歧义、不清楚、或触及边界的点，都要提问，**不得自行假设、不得断章取义**。
2. **保留三件套结构。** 每个插件至少包含 `app.json`、`__init__.py`、`main.py`，结构见 `references/01-structure-and-opk.md`。
3. **批量与重复操作必须限速——"操作"不只是发消息。** 连发消息、逐群推送、改群名、改群名片、禁言、踢人、退群、撤回、删好友、邀请入群、处理申请，全部按 `references/04-risk-control.md` 的间隔**串行**执行，禁止并发。**量级大时**（消息累计超 30 条、单条内容长或带多图/链接、同一内容群发；管理动作超 5 条即需提风险、超 10 条必问）1~3 秒不够用：先向用户说明封号风险，再问「你希望每隔多少秒发一条 / 执行一条」，用用户给的数值，不得自己拍。**退群属于高危动作**，用户没明确要求就不要写。
4. **失败要说话，不要沉默。** API 调用、文件读写、绘图失败时 `try/except` 后用 `reply` 把错误反馈到当前会话；只有"无关消息直接 return"这种场景才允许静默。
5. **调试用 `reply`，不用 `print`。** 青果环境下 `print` 不会显示在任何地方，用 `reply` 把调试信息发到当前群/私聊；多条就逐条发；调试阶段不遵守限速间隔。
6. **数据按实际情况灵活分，但必须封顶。** 先问清数据主体、访问模式、保留策略，再决定怎么分（怎么分没有标准答案，不要照搬别的插件）；任何数据文件都不得设计成无限增长，记录类数据必须有清理或归档出口，消息处理路径上不得反复全量读大文件。详见 `references/05-data-and-timer.md`。
7. **交付出 `.opk`，但要先确认再打包。** 代码写完后，先跟用户确认"功能全部写完、可以上服务器测试了"，**再问 `app.json` 的 `author` 要署什么名字**，得到确认后再打包成 opk：zip 内**直接放 py/json 等文件，不套文件夹**，然后改后缀为 `.opk`。打包后提醒用户随时可以回来继续修改、改完重新打包。用户明确只要源码文件夹时才不打包。
8. **改别人的插件就最小改动。** 不顺手重构、不换风格、不动数据层、不改插件身份（`name` / `namespace` / `datafile`）；数据结构要变时，必须保证老数据还能读。改完说明"改了哪些函数、行为怎么变、有什么风险"。
9. **路径是骰子端的，不是本机的。** 插件里的 `./data/images/`、`./plugin/data/` 指**骰子所在服务器**的工作目录。用户说"文件夹里的图"时，先问清图片在服务器上还是他电脑里；素材必须先由用户上传到服务器的 `data/images/<插件名>/` 下，插件才读得到。**禁止在本地磁盘搜索这些目录**——骰子在服务器上跑，本地本来就没有。
10. **`main.py` 头注释末尾必须带署名行。** 头部注释块最后一行之后**空一行**，再写固定一句：
    ```python
    # 本插件由临皋闲人（3149790940）封装的 AI Skill 辅助生成
    ```
    一个字都不要改，也不要挪位置。这是全插件唯一允许出现该署名的位置（`app.json` 的 `author` 是插件作者，按第 7 条单独问用户）。

### 绝对禁止

1. 禁止用 `print` 调试或输出日志。
2. 禁止改 `app.json` 里除 `name` / `author` / `namespace` / `info` 之外的字段，其余一律原样保留。
3. 禁止"优化" `getData` / `setData` 的内部实现（含去掉锁、改成原子写入）。这是权衡稳定性后的定论，大面积加锁会导致青果异常卡死。
4. 禁止引入 `schedule` 等骰子环境不自带的第三方库；定时任务用标准库线程轮询，见 `references/05-data-and-timer.md`。
5. 禁止编写"风控检测 / 自动解封 / 失败重试到成功"之类逻辑——腾讯的风控无法从客户端检测，表现为直接踢下线封号，插件层面只能做预防性限速。
6. 禁止过度防御式代码（到处 `try/except: pass`、重复校验、无意义兜底分支），清单见 `references/07-style-and-antipatterns.md`。
7. 禁止把署名写进 `main.py` 头注释之外的任何位置——代码正文、函数注释 / docstring、`app.json`、交付说明都不行。头部那行署名本身是必写的（见「必须先做」第 10 条）。
8. 禁止在本地文件系统里搜索 `data/images`、`plugin/data` 这类插件运行目录；禁止把"本机找到的文件"当成插件能读的文件；禁止假设用户电脑上的路径在服务器上存在。
9. 禁止用多线程 / 线程池 / 协程并发调用批量操作接口（发消息、改群名、禁言、踢人、撤回等一律串行）；禁止对管理类操作的失败自动重试。
10. **禁止用 `\d+` / `[-]?\d+` / `[+-]?\d+` 去匹配 `message_id`，禁止 `int(message_id)`。** 部分协议端版本的 id 已经是 Base64 风格字符串（如 `ZboWS4aWxK9p...`），窄正则匹配不到、`int()` 直接崩。统一用 `([^,\]]+)` 提取，并按字符串传递。

## 工作流

### 第 0 步：需求澄清（强制，不可跳过）

逐项向用户确认下列内容，**用户已经明确说过的不要重复问**，缺失或有歧义的一律提问：

| 类别 | 要问清楚的点 |
| --- | --- |
| 目标 | 插件解决什么问题？一句话目标是什么？ |
| **协议** | **骰子挂的是哪套协议端——napcat 还是 LLBot？协议端版本是多少？** 决定能用哪些扩展接口，写代码前必须问清（见 `references/08-api-lookup.md`） |
| 触发方式 | 群聊指令 / 私聊指令 / 事件触发（入群、退群、加好友、撤回、戳一戳）/ 定时任务，各是哪些？ |
| 指令词表 | 每条指令**精确的原文写法**：前后缀、是否要 @ 骰子、参数格式、是否用 `《》` 包裹。必须拿到示例原文，不能靠猜。 |
| **指令格式** | **动笔前必须问用户选哪种**：① **固定文本直接触发**（如「排单」「查单」，不加任何符号，参考插件那种）；② **以 `.` 或 `/` 开头触发，两个符号都要兼容**。选 ① 要确认指令词足够独特、不会误触闲聊；选 ② 要确认是否把全角符号也一并兼容。**默认只做一种，不要自作聪明两套都上**——混用会让匹配逻辑变复杂，除非用户明确要求。 |
| **引用消息** | 是否需要**引用某条消息再发指令**？要的话再问两层：① 只是"剥掉 reply 段再匹配指令"，还是要把**被引用消息的内容**读出来用？② **被引用的消息会不会是合并转发卡片**（会的话得再用 `get_forward_msg` 展开一层）？没引用时希望提示什么？ |
| 权限 | 谁能用？骰主 / 指定管理员 / 群管理 / 所有人？需要群白名单吗？ |
| 数据 | 存什么？**数据主体是谁（用户 / 群 / 记录 / 全局配置）？平时只查某一条还是要全量遍历？保留多久、满了怎么办、要不要能手动删？** 会不会和别的插件共用数据？ |
| 输出 | 纯文本 / 多段文本 / 合并转发 / 图片 / 音乐卡片；要不要 @ 某人；发给本群还是别的群。 |
| 定时任务 | 几点触发？触发时对哪个群做什么？群号是写死还是读配置？ |
| 图片 | 要不要画图？画什么？尺寸？ |
| **素材来源** | 要用到现成的图片/文件吗？**这些素材现在在哪——服务器上的哪个目录，还是用户电脑里？** 多少张、什么格式？由谁、怎么传到服务器的 `data/images/<插件名>/` 下？插件读不到用户电脑里的文件。 |
| 跨插件 | 是否要读/写其他插件的数据？（若是，必须走跨插件锁流程） |
| 命名 | 插件英文名是什么？（同时决定 namespace、文件夹名、`datafile`） |
| 边界 | 有没有批量 / 高频操作？**只是发消息，还是要批量做管理动作（改群名、群名片、禁言、踢人、退群、撤回、删好友、邀请）？一次多少条、单条多大、发多久？** 消息超 30 条、管理动作超 5 条就要提风险，超 10 条必须问用户「每隔多少秒执行一条」（见 `references/04-risk-control.md`）。 |
| 交付 | 只要源码文件夹，还是要产出 `.opk`？ |

**遇到以下情况必须停下来发问，不得自行决定**：协议端不明（napcat 还是 LLBot、版本多少）、指令文案不确定、**指令格式未确认（固定文本还是 `.` / `/` 前缀）**、**涉及引用消息但没说清是只匹配指令还是要读被引用内容**、权限模型不确定、要写入其他插件的目录、涉及批量或高频操作、要用公开文档里没写的接口、用户描述前后矛盾、出现了"大概 / 应该 / 差不多"这类描述。

**如果是改造已有插件**，澄清重点换成这几条：要改哪条指令 / 哪段行为、现在的实际表现是什么、期望变成什么、数据结构要不要变（老数据怎么办）、哪些部分不能动。详见 `references/09-takeover-existing-plugin.md`。

### 第 1 步：判断起点——从零写，还是接管已有插件

- **从零写**：从 `templates/` 复制三件套并改名，细节见 `templates/README.md` 与 `references/01-structure-and-opk.md`。
- **接管已有插件**（用户给了 `.opk`、插件文件夹，或只有 `main.py`）：走 `references/09-takeover-existing-plugin.md`。先用 `scripts/unpack_opk.py` 解包，读懂了再改，最小改动，不动数据层。

### 第 2 步：实现

按下面的索引读取对应 reference，逐条落地。

### 第 3 步：自检

交付前逐条核对：

- [ ] `app.json` 只改了 `name` / `author` / `namespace` / `info`，且 `namespace` 与 `name` 逐字符相同（含大小写）
- [ ] `__init__.py` 内容正确（有额外模块时已一并 import）
- [ ] `Event` 类里只保留了本插件真正需要的钩子，无关钩子可以留空
- [ ] 所有批量 / 重复动作（发送 + 管理操作）都有间隔且串行执行，量级大时用的是用户确认过的间隔，不是自己拍的数值
- [ ] 所有会失败的调用都有 `try/except` 且有 `reply` 反馈
- [ ] 无关群聊/无关消息直接 `return`，不产生任何回复
- [ ] 定时任务用 `init()` 启线程 + 轮询 + 去重，且线程内有 `try/except`
- [ ] 图片路径符合 `./data/images/<插件名>/` 规则，发送写法正确
- [ ] **数据结构按本插件实际情况设计（不是照搬别的插件），每个数据文件都有增长上限，记录类数据有明确的清理/归档出口**
- [ ] 没有 `print`、没有 `schedule`、没有多余第三方依赖
- [ ] 指令格式按用户选定的方案实现（固定文本，或 `.` / `/` 前缀兼容），没有两套混着来
- [ ] 若涉及引用消息：匹配指令前已剥离 `[OP|CQ:reply,id=...]`；要读被引用内容时，未引用的情况有明确提示；若被引用的可能是合并转发，已按 `get_forward_msg` 再展开一层
- [ ] 所有 `message_id` 都用 `([^,\]]+)` 提取、按字符串传递，没有 `int()`、没有 `\d+` 窄正则
- [ ] 没有过度防御式写法；`main.py` 头注释末尾空一行后带有固定署名句，且别处没有出现该署名
- [ ] 打包前已向用户确认「功能写完、可以上服务器测试」，并确认过 `app.json` 的 `author` 署名

### 第 4 步：打包 opk

**打包前必须跟用户确认两件事**，缺一件都不能打：

1. **功能是否全部写完、是否可以上服务器测试。**
2. **`app.json` 的 `author` 字段署什么名字。** 直接问用户"作者署名想写什么"，等他给答案——可能写本名、网名、群名、团队名，也可能要求带 QQ 号。**不要默认填 skill 整理者的名字，也不要留空或自作主张填插件名。** 用户说"随便"时给建议（他的网名或维护组名），但仍要他点头。

得到确认后再打包，**不要写完就自作主张封装**。

按 `references/01-structure-and-opk.md` 的步骤打包；可用 `scripts/pack_opk.py` 直接把插件文件夹打成 `.opk`。

打包完成后，告诉用户：**这不是终稿，随时可以回来继续改，改完再说一声重新打包即可**（同一套文件重新执行打包命令就行，数据不会丢，因为数据存在骰子的 `plugin/data/` 里，不在 opk 内）。

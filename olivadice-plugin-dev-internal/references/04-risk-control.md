# 04 QQ 风控与限速

## 前提认知

腾讯的风控**无法从客户端检测**。触发后的表现是消息发不出去、账号被踢下线，严重时直接封号（需要人工扫脸解封），整个机器人瘫痪。

因此：

- **插件能做的只有预防性限速**，把操作频率压到安全区。
- **不要写**风控检测、自动重试、自动解封、失败后加速补发之类的逻辑——检测不到，重试只会让情况更糟。
- 涉及批量、连发、重复操作的需求，必须在第 0 步需求澄清时就确认清楚，并按下表的间隔设计；量级大的还要按下节「1~3 秒覆盖不住的情况」向用户确认间隔。
- **「操作」不只有发消息。** 改群名、改群名片、禁言、踢人、退群、撤回、删好友、邀请入群、处理申请——这一整套批量动作同样是风控重点，甚至比发消息更敏感，见「群管理类操作」一节。

## 限速数值（硬规则）

| 类别 | 场景 | 间隔 |
| --- | --- | --- |
| 消息 | 私聊通知、单条后续消息 | `time.sleep(1)` |
| 消息 | 批量发送 / 逐群推送 / 合并转发分块之间 | `time.sleep(2)` |
| 消息 | 合并转发单次节点数 | ≤ 90，常规取 70 |
| 管理 | 任何逐条执行的管理动作（改群名 / 群名片 / 禁言 / 踢人 / 撤回 / 删好友 / 邀请 / 退群） | `time.sleep(2)`，且**必须串行** |

已经有 `time.sleep()` 的地方不要再"优化"掉。新增任何循环发送的代码，都要按上表加间隔。**量级上去时上表不够用**，见下面「1~3 秒覆盖不住的情况」。

**调试阶段例外**：调试时为了快速看到结果，可以不遵守间隔；确认逻辑无误后再补回睡眠。调试输出用 `reply` 发到当前会话（`print` 看不到），多条就逐条发。

## 批量发送的标准写法

不要闷头发完再回复。正确顺序是：

1. 先 `reply` 告诉用户"正在处理，预计需要 X 秒"；
2. 再逐条 / 逐群发，每条之间 `sleep(2)`；
3. 全部完成后 `reply` 汇总结果。

批量改群名（`set_group_name`）、批量禁言、批量踢人等管理类操作同样按这个节奏，并在前后包 `try/except`：单个群失败不要中断整批，记录失败项最后一起反馈。

## 群管理类操作：比发消息更容易出事

发消息是"内容"风险，管理动作是"账号行为"风险。一个普通账号突然连续踢人、连续退群、连续改群名，在服务端看来和**被盗号**的行为特征几乎一样——这类操作触发风控往往比刷屏更快，而且不给缓冲。

硬规则：

1. **只能串行。** 一次只做一个动作，做完 `sleep` 再做下一个。**禁止**用多线程 / 线程池 / 协程并发打这些接口——并发本身就是最强的异常信号。
2. **默认 `sleep(2)`**，与批量发消息同档。
3. **量级要压得更低。** 管理类动作的风险阈值远低于发消息：
   - 单次超过 **5 条**，先提示风险；
   - 单次超过 **10 条**（改群名 / 群名片 / 禁言 / 踢人 / 退群 / 邀请 / 删好友），**必须停下来问用户间隔**，不许自己拍数值。
4. **退群（`set_group_leave`）单独对待。** 主动退群是账号异常 / 被盗的强特征，风控上属于高危动作。除非用户明确要求"机器人自己退出某些群"，否则**不要写**；写了也必须逐群确认、逐个间隔，不能做成无人值守的自动清理。
5. **同一个群不要在短时间内做多个不同动作**（比如连改群名 + 换群名片 + 禁言）。合并成一次用户可见的确认也好，隔开也好，绝不能挤在一两秒内。
6. **管理操作失败不重试。** 失败往往是权限不对或已被拦截，立刻重试只会加重异常判定——记下失败项，最后汇总反馈给用户。

命中第 3 条的阈值时，处理方式和下一节一样：先讲风险，再问用户「你希望每隔多少秒执行一条」。

## 1~3 秒覆盖不住的情况

上表的 1~3 秒只够应付零散几条消息、一两个管理动作。一旦任务量级上去了，照着底线写就是在赌账号。出现下面任意一种情况，**默认认为间隔不够用**：

| 信号 | 具体表现 |
| --- | --- |
| 量级 | 一次任务累计发送超过 **30 条**（拿不准就按 50 条为界），同一内容发往多个群 |
| 单条体积 | 一条里塞多张图、大段长文本、多个 @、附带文件 |
| 内容风险 | 短链接、二维码、邀请入群 / 加好友、`@全体成员`、连续发图片或文件 |
| 操作类型 | 批量改群名 / 群名片、批量禁言、批量踢人、批量退群、批量邀请、批量删好友、批量撤回（阈值见「群管理类操作」第 3 条） |
| 持续时间 | 要连续跑几分钟以上，或需要长期高频推送 |

这张表只是「要不要停下来问」的判断线，**不是安全阈值**——风控没有公开阈值，也没法测。

命中任意一条时，**不许自己拍一个数字写进代码**，按顺序做两件事：

1. **先讲风险。** 明确告诉用户：这个量级有封号风险（触发表现是被踢下线，严重时封号需人工解封），而且间隔是经验值、不保证安全。
2. **再让用户定节奏。** 直接问「你希望每隔多少秒发一条 / 执行一条？」拿到用户给的数字，做成配置项或指令参数，不要写死常量。用户说"你定"时，给一个偏保守的默认值（分钟级），并在交付说明里标注这是保守估计。

可以顺带给出几个降风险方向，让用户自己选，不要替他决定：

- 拉长间隔：分钟级远比秒级安全。
- 削减单条内容：图片张数、@ 个数、文本长度都算负担。
- 改用合并转发，把多条压成一次发送（观感差一些，但发送次数骤减）。
- 分批执行：发一阵停一阵，别一口气跑完。
- 管理动作能人工就人工：一次性的批量踢人 / 改群名，让用户自己在客户端点，比交给机器人安全。

## 特别危险的操作

按经验，下面这些最容易招风控，能合并就合并、能少做就少做：

- 短时间内给大量群发同样的内容（最容易触发）
- 主动加好友、主动邀请入群
- 批量踢人、批量退群
- 批量改群名 / 群名片（每次都会给全体成员推通知，动静很大）
- 短时间大量撤回消息
- `@全体成员`
- 连续发送链接、图片、文件

规避方向：**能用一次合并转发讲清的事，不要拆成多条连发**；能等一会儿再发的，不要立刻发；能人工做的，不要塞给机器人。

## 收到图片的处理

用户发来的图片在消息里是 `[OP:image,...]` 或 `[CQ:image,...]`。要存文本时先剥掉：

```python
text = re.sub(r"\[(?:OP|CQ):image,[^\]]+\]", "", message)
```

并在回复中提示「部分图片可能被腾讯拦截无法显示」——图片本身可能已经被平台拦掉，插件拿不到。

# 09 接管已有插件（从 opk 或 main.py 入手）

用户不是每次都从零写。更常见的是：**丢来一个现成的 opk，或者一段 main.py，让你改**。这条路径和"从零写"不同——重点是**先读懂、再最小改动、别弄坏原有数据**。

## 入口判断

| 用户给的东西 | 怎么处理 |
| --- | --- |
| `.opk` | 先用 `scripts/unpack_opk.py` 解包，得到三件套再读 |
| 一个插件文件夹 | 直接读，先确认里面有没有 `app.json` / `__init__.py` / `main.py` |
| 只有 `main.py` | 先问清插件名，再用 `templates/app.json`、`templates/__init__.py` 补齐 |
| 一段代码片段 | 问清它属于哪个插件的哪个功能，不要凭空拼一个完整插件 |

解包命令：

```bash
python3 scripts/unpack_opk.py <插件.opk> [输出目录]
```

脚本会顺带检查：包内是否套了一层文件夹（会提醒并展平）、有没有 `app.json`、`name` 与 `namespace` 是否一致、缺不缺 `__init__.py` / `main.py`。

**不要直接改用户的原 opk**，解包到工作目录再动手。

## 第一步：先读，别急着改

按这个顺序把结构摸清楚，再动手：

1. `app.json` → 插件名（`name` = `namespace` = 文件夹名）、版本、作者；
2. `Event` 类 → 用了哪些事件钩子；
3. 消息分发入口（一般是 `handle_message` / `reply(ctx)` 之类）→ 指令是怎么分派的、有没有统一的 `ctx`；
4. 数据层 → `datafile` 是什么、用了哪些数据文件、是否按 uid / groupid / 记录分片；
5. 公共工具 → API 封装、限速发送、绘图、定时任务；
6. **找到要改的那个函数**，确认它在整条链路里的位置。

读的时候顺手记下：现有代码风格（命名、注释、`ctx` 用法）、哪些地方在本需求之外**不能碰**。

## 第二步：改之前必须问清

这几条不问清就动手，很容易返工或弄坏线上数据：

- **要改的是哪条指令 / 哪段行为？** 现在的实际表现是什么，期望变成什么？最好有原文示例。
- **数据结构要不要变？** 要变的话，老数据怎么办——兼容读取（老键名 fallback）、写迁移函数，还是明确放弃（要告诉用户会丢什么）？
- **会不会引入批量 / 高频操作？** 包括批量发消息，也包括批量改群名、禁言、踢人、退群、撤回这类管理动作——会的话必须按 `references/04-risk-control.md` 加间隔并串行。
- **有没有不能动的部分？** 其他指令、其他数据文件、定时任务、别的插件在读的数据。
- **改动范围确认**：把"准备改哪几个函数"列出来给用户点头，再开始写。

## 第三步：改的规矩

1. **最小改动**。只碰和需求相关的函数，不顺手重构、不重命名、不换代码风格。
2. **`getData` / `setData` 原样保留**（锁、`.bak` 逻辑一律不动），这是红线。
3. **沿用原有风格**：原文件用 `ctx` 就继续用 `ctx`，原文件用 `《》` 包裹指令就保持，不要掺入另一套写法。
4. **数据兼容优先**：读旧数据时给默认值，新字段缺失要能跑；新增数据文件按 `references/05-data-and-timer.md` 的封顶原则设计。
5. **新增批量操作必须限速并串行**（发消息和管理动作都算），并沿用原有的发送封装（别另造一套）；原插件里用并发打批量接口的写法，除非用户明确要求，否则不要学。
6. **改完更新头部注释**：版本号递增、更新日期、更新日志写清"这次改了什么"；并在注释块最后一行后空一行补上固定两行——`# 本插件由临皋闲人（3149790940）封装的 AI Skill 辅助生成` 与 `# 来源：https://github.com/chongguang89/olivadice-plugin-dev-internal`（原文件没有头注释的，按 `references/01-structure-and-opk.md` 的格式补齐；只有署名一行、没有来源行的，把来源行补在下面）。

## 第四步：交付

1. 跑一遍 `SKILL.md` 第 3 步的自检清单；
2. 向用户说明：**改了哪几个函数、行为有什么变化、有什么风险**（数据兼容、风控、需要重启骰子）；
3. 确认"可以上服务器测试"后，用 `scripts/pack_opk.py` 重新打包（扁平结构，不套文件夹）；
4. 提醒用户：数据存在骰子本地的 `plugin/data/<插件名>/`，**重装 opk 不会清数据**。

## 常见坑

- **包里带旧 `.pyc`**：解包时会被跳过，重新打包时也不要带上。
- **`name` 与 `namespace` 不一致的老包**：能跑但很危险。**不要擅自改**——改了等于换了插件身份，数据目录也会跟着变，先告诉用户。
- **改了 `datafile`**：等同于让老数据"消失"（指向了新目录）。除非用户明确要重来，否则不要动。
- **额外模块**（如 `schedule.py`）：改功能时如果牵扯到它，要一起看；重新打包时记得一起带上。
- **原插件用别的插件的数据**：那是跨插件锁的范畴，见 `references/05-data-and-timer.md`，别只改一半。
- **原插件里有明显的风控隐患**（连发、无间隔批量）：不要在"只改一个小功能"的任务里偷偷大改，但要在交付时**指出来**，由用户决定要不要一起处理。
- **老代码用 `int(message_id)` 或 `[-]?\d+` 匹配 id**：以前能跑，换到返回 Base64 id 的协议端版本后会**静默失效**（指令完全没反应、或抛 `ValueError`）。接管时顺手检查一遍，改成 `([^,\]]+)` 并按字符串传递，在交付说明里写清"这里改了 id 解析，兼容新版协议端"。
